## Context（背景）

当前仓库是一个新的前后端分离项目。前端是 Next.js 应用，后端是 FastAPI 服务，音频文件本地保存到 `storage/audio/`。这个变更是第一个业务能力，需要先建立离线上传与播放基础，再继续做后续转写和 AI 分析。

初始实现只需要在单人本地开发环境中配合 SQLite 正常工作。不需要多用户归属、云对象存储、后台 AI 处理或实时音频采集。

## Goals / Non-Goals（目标 / 非目标）

**目标：**

- 允许用户从网页上传一个本地音频文件。
- 将音频文件持久化到后端文件系统。
- 将录音元数据持久化到 SQLite。
- 在前端展示已上传录音列表。
- 使用后端音频 URL 在浏览器中播放选中的录音。

**非目标：**

- 不做实时录音或麦克风采集。
- 本变更不做转写时间轴、AI 总结、高光片段或玩家沟通风格分析。
- 不做用户账号、访问控制、支付或移动端 App。
- 不做云存储或分布式处理。

## Decisions（技术决策）

1. 使用后端管理的本地存储保存上传音频。

   原因：本地存储是离线 MVP 最小且可靠的路径，也符合当前 `storage/audio/` 项目结构。

   备选方案：直接把文件存进 SQLite。拒绝原因是二进制音频会让数据库变大、难以检查，也不利于音频流式响应。

2. 使用 SQLAlchemy 将录音元数据保存到 SQLite。

   原因：SQLite 让 MVP 本地开发配置简单，SQLAlchemy 则保留了未来迁移到其它关系型数据库的空间。

   备选方案：在音频文件旁边保存 JSON 元数据文件。拒绝原因是列表、排序和未来分析状态更新使用关系表更简单、更安全。

3. 在服务端生成录音 ID 和存储文件名。

   原因：上传文件名可能冲突，也可能包含不安全字符。原始文件名只应作为展示元数据保存。

   备选方案：直接使用原始文件名作为存储文件名。拒绝原因是会带来文件名冲突和路径安全风险。

4. 通过后端端点暴露音频播放，而不是暴露直接文件系统路径。

   原因：前端不应依赖服务端文件系统布局，未来如果增加授权或签名访问，也可以沿用同一路由。

   备选方案：把 `storage/audio/` 作为静态目录直接服务。拒绝原因是它会暴露实现细节，也会让后续访问检查变得别扭。

## Risks / Trade-offs（风险 / 权衡）

- 上传文件可能很大 -> 使用可配置的最大上传大小，并返回清晰的校验错误。
- 浏览器播放依赖音频格式支持 -> 接受常见浏览器友好的音频格式，并返回保存的 MIME type。
- 本地存储可能占满磁盘 -> 文档中说明存储位置，删除和保留策略暂不纳入本次变更。
- SQLite 与本地文件系统可能因部分写入成功而不一致 -> 先保存文件，再创建元数据；如果失败，尽量清理孤儿文件。

## Migration Plan（迁移计划）

这是第一个带持久化的业务能力，因此没有既有用户数据需要迁移。实现时应按照选定的数据库初始化方式，在本地设置或服务启动时创建 SQLite 表。

MVP 开发阶段的回滚方式很直接：移除新增 API 路由、前端上传/播放 UI、SQLite 表，以及 `storage/audio/` 中的已上传文件。

- 除常见浏览器格式外，还需要正式支持哪些音频格式？
